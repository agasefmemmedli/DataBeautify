# Project Context for AI Agents

_Этот файл содержит критичные правила и паттерны проекта, которые AI-агенты должны соблюдать при изменении кода._

---

## Technology Stack & Versions

- TypeScript `5.7.3` (strict mode, CommonJS, target `ES2020`)
- Node.js + VS Code Extension API (`@types/vscode` `^1.74.0`, `engines.vscode` `^1.74.0`)
- Сборка: `esbuild` `^0.27.3`, компиляция `tsc`
- Линтинг: `eslint` `^8.28.0` + `@typescript-eslint` (`parser`/`eslint-plugin` `^5.45.0`)
- Тесты: `mocha` `^11.7.5` + `@vscode/test-electron` `^2.5.2`
- Ключевые runtime-зависимости форматирования:
  - `prettier` `^3.8.1` + набор prettier-плагинов
  - `js-beautify` `^1.15.4`
  - `fast-xml-parser` `^5.3.6`
  - `xml-formatter` `^3.6.0`
  - `jsonrepair` `^3.13.2`
  - `sql-formatter` `^15.7.2`

## Critical Implementation Rules

### 1) Архитектурные границы

- Точка входа расширения: `src/extension.ts`.
- Определение формата централизовано в `src/detector.ts`.
- Языковые/форматные обработчики находятся в `src/formatters/*`.
- Новую логику форматирования добавлять через отдельный обработчик/модуль, а не раздувать `activate()` или `beautify()`.

### 2) Конвенции TypeScript и импорта

- Обязателен `strict: true` (не отключать для “быстрого фикса”).
- Используется `module: commonjs`; импорты и экспорт держать совместимыми с текущей схемой.
- Для модулей-форматтеров допускается ленивый `require(...)` внутри функций (паттерн уже используется для тяжёлых зависимостей).

### 3) UX и обработка ошибок в расширении VS Code

- При отсутствии активного редактора/пустом документе показывать `vscode.window.showErrorMessage`/`showWarningMessage`.
- Фолбэки обязательны: если deep-formatter не справился, пробовать безопасный альтернативный путь.
- Ошибки сообщать пользователю ясно и с контекстом (например, место ошибки валидации XML).

### 4) Правила редактирования документа

- Изменения текста должны применяться через общие утилиты (паттерн: `applyEdit`), а не напрямую в нескольких местах.
- Уважать настройки редактора (`tabSize`, `insertSpaces`) при формировании результата.

### 5) Тестовые правила

- Основной шаблон e2e/extension-тестов: `src/test/suite/formats/test_*.test.ts`.
- Для каждого нового поддерживаемого формата добавлять отдельный файл `test_<format>.test.ts` по существующему паттерну.
- Не менять устоявшуюся структуру тестов (`suite(...)`, `test(...)`, запуск через команду расширения), если нет веской причины.

### 6) Нейминг и структура

- Имена файлов-форматтеров: `snake_case` (например, `json_deep_formatter.ts`).
- Тестовые файлы: `test_<format>.test.ts`.
- Экспортируемые хендлеры форматов именовать как `handle<Format>` (например, `handleXML`, `handleJSON`).

### 7) Workflow и quality gates

- Перед тестами выполняются `compile` и `lint` (`pretest`), поэтому изменения должны проходить оба шага.
- Скрипты проекта:
  - `npm run compile`
  - `npm run lint`
  - `npm test`

### 8) Critical Don't-Miss Rules

- Не ломать fallback-цепочку: если основной форматтер падает, выполнять безопасную альтернативную попытку.
- Не пропускать проверки `activeTextEditor` и пустого документа; всегда делать ранний выход с UX-сообщением.
- Не дублировать эвристику определения форматов в нескольких местах; источник истины — централизованный детект.
- Не игнорировать настройки редактора (`tabSize`, `insertSpaces`) при генерации форматированного вывода.
- Не выносить тяжёлые зависимости на верхний уровень без необходимости, чтобы не ухудшать время активации extension.
- Не добавлять новый формат без отдельного теста `test_<format>.test.ts`.
- Не менять порядок recovery для `unknown` без отдельной проверки регрессий.
- Не внедрять небезопасные механизмы обработки контента (например, eval-подобные подходы).

## Usage Guidelines

**For AI Agents:**

- Читать этот файл перед реализацией любых изменений.
- Следовать всем правилам и при конфликте выбирать более строгий вариант.
- При обнаружении нового устойчивого паттерна обновлять этот файл.

**For Humans:**

- Держать файл компактным и ориентированным на необvious правила для агентов.
- Обновлять контекст при изменении стека, quality gates или архитектурных паттернов.
- Периодически пересматривать и удалять устаревшие/очевидные правила.
